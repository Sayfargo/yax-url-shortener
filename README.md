## Оптимизация производительности и профилирование

Через нагрузочное тестирование с помощью **k6** было проведено профилирование памяти с использованием **pprof**.

### Выявленные проблемы

1. **Оверхед генератора ID:** Изначально для генерации коротких кодов использовалась библиотека `matoous/go-nanoid/v2`. Анализ `heap`-профиля показал, что на каждый вызов `Generate()` библиотека выполняла лишние аллокации в куче. Поскольку алфавит и длина идентификаторов в сервисе статичны, пересоздание внутренних структур на каждый запрос было избыточным.
2. **Тяжелая валидация:** Сторонняя библиотека `validator`, применявшаяся для проверки URL, использовала рефлексию и создавала лишний оверхед для такой тривиальной задачи, как проверка структуры URI.

### Что было сделано

* **Собственный генератор:** Я инкапсулировал и адаптировал безопасный алгоритм генерации под конкретные нужды приложения, избавившись от динамических аллокаций. Все параметры теперь инициализируются один раз.
* **Кастомный валидатор:** Пакет `validator` был заменен на легковесную, специализированную функцию валидации URI без привлечения механизма рефлексии.

### Результаты оптимизации (Сравнение Heap-профилей)

Благодаря внесенным изменениям, общее количество выделяемой памяти (`cum`) в методе `CreateShortURL` сократилось **более чем в 2 раза** — с **81.9 МБ до 38.3 МБ**, а доля функции в общем пуле аллокаций снизилась с **51.09% до 48.84%**.

#### До оптимизации
Основная нагрузка приходилась на генератор строк (строка 304) и сборку логов/моделей:
```text
ROUTINE ======================== internal/service/service.go
   2424860   81876839 (flat, cum) 51.09% of Total
         .          .    298:   if err := validateURL(url); err != nil { ... }
         .          .    302:   for attempt := 0; attempt < 3; attempt++ {
   1310740    3748001    304:           shortCode, err := s.generator.Generate()
         .    2625854    309:           shortenedURL := model.ShortenedURL{ ... }
```

#### После оптимизации
Память в `generator.Generate()` упала почти в 12 раз по `cum` (с **3.7 МБ до 294 КБ**), снизилось давление на аллокатор в смежных структурах:
```text
ROUTINE ======================== internal/service/service.go
    983047   38335794 (flat, cum) 48.84% of Total
         .     688222    298:   if err := validateURL(url); err != nil { ... }
         .     294916    304:           shortCode, err := s.generator.Generate()
         .     622601    310:           shortenedURL := model.ShortenedURL{ ... }
```

#### Сравнение через pprof diff
Сравнение профилей наглядно фиксирует чистое снижение вызовов `runtime.mallocgc` (выделение памяти в куче) на **~4.1 МБ** в рамках тестового сценария:
```text
Showing nodes accounting for -6161.39kB, 44.46% of 13859.39kB total
      flat  flat%   sum%        cum   cum%
-4102.80kB 29.60% 29.60% -4102.80kB 29.60%  runtime.mallocgc
   -1026kB  7.40% 37.01%    -1026kB  7.40%  bufio.NewWriterSize (inline)
 -525.43kB  3.79% 33.41%  -525.43kB  3.79%  internal/service.(*URLShortenerService)
```

**Итог:** Устранение лишних аллокаций разгрузило сборщик мусора, снизило задержки на пиковой нагрузке и уменьшило потребление CPU сервером.
